# ADR-0001: Cold Storage の初期Parquetレイアウトに時刻順Long形式を採用する

- 状態: 採用（初期実装の方針。R2上での検索実測により見直し可能）
- 決定日: 2026-11-05
- 対象: Archiverが生成するCold StorageのParquet
- 関連: [時刻・月別パーティション設計メモ](cold-storage-time-and-partitioning.md)

## 背景

VictoriaMetrics (vmsingle) に保持するHotデータを約3か月とし、それ以前の履歴を
S3互換オブジェクトストレージのCold Storageへ移す構想である。
Query APIはHotを優先し、Coldはまれな過去データ検索に利用する。
想定クエリは系列と時刻範囲を指定した単純な時系列SELECTが中心である。

Coldの検索頻度が低いため、単一クエリの数msの差より、
保存容量、Archiverの実装容易性、系列追加への追従性を重視する。
低頻度アクセス系ストレージクラスでは、取得料金や最低保存期間なども別途考慮する。

## 決定

初期Archiverは、**時刻順Long形式のParquet** を出力する。

- 行データは時刻昇順で配置する。系列別のソートは初期実装では行わない。
- 圧縮コーデックにはZSTDを使用する。
- サンプル時刻および月別パーティション境界はUTCとする。
- 月ごとの範囲は `[月初00:00 UTC, 翌月初00:00 UTC)` とする。
- Parquetファイルは生成後に変更しない（immutable）。
- ファイル配置はHive形式の `year=YYYY/month=MM/` を第一候補とする。
- Query APIによる検索時は対象月を明示的に指定し、パーティションプルーニングを利用する。

実験用スキーマは `timestamp TIMESTAMPTZ, metric VARCHAR, value DOUBLE` の3列だった。
これは**本番Archiverの確定スキーマではない**。VictoriaMetricsのメトリクス名、
`site_id`・`sensor_id`などのラベル群、系列識別子の表現は実装前に決定する。

## 比較した選択肢と結果

DuckDB CLIで2026年10月の31日、通常値200系列（1分間隔）と
ON/OFF値100系列（毎日再記録＋約7日ごとの変化を模擬）を生成した。
同一サンプル8,931,600件を、ZSTD圧縮Parquetの以下の3形式で比較した。

| 形式 | ファイルサイズ | 月間平均・単一系列 | 1時間平均・単一系列 |
| --- | ---: | ---: | ---: |
| Wide（timestamp＋300列） | 65,853,565 B | 約5.2～5.5 ms | ウォーム時7.5～8.8 ms |
| 時刻順Long（timestamp, metric, value） | 44,438,014 B | 約18.8～19.3 ms | 9.3 ms（単発） |
| 系列順Long（metric, timestampでソート） | 75,504,133 B | 8.4 ms（単発） | 4.5 ms（単発） |

- 時刻順LongはWideより**約32.5%小さい**（WideはLongの約1.48倍）。
- 時刻順Longは列ごとの圧縮効率が高く、`timestamp` が816,952 B、
  `metric` が24,694 B、`value` が43,210,069 B（Parquetの列チャンク合計）。
- 系列順Longでは `timestamp` が9,929,284 B、`value` が65,542,134 Bとなり、
  時刻順Longよりファイルサイズが約69.9%増えた。
- Wideは単一系列で列プルーニングが効き、ローカルの月間平均クエリで高速だった。
- いずれもローカルではmsオーダーで検索できた。計測環境、キャッシュ、
  クエリ実行順の影響があるため、ベンチ結果から一般的な順位を断定しない。
- 実験データは合成波形であり、数値のエントロピー、実機での欠損・変化頻度、
  タグ構成が異なると圧縮率も変わり得る。

## その他の検証事項

- DuckDBからCloudflare R2への接続と、Parquetの書き込み・読み取りを確認した。
- ローカルParquetで、月をまたぐ複数ファイルの読み取り、
  `union_by_name=true` による列差異の吸収を確認した。
- Hiveパーティションを使用したクエリでは、
  `Scanning Files: 1/2`, `Total Files Read: 1` を確認した。
- **R2上の複数ファイル検索、Range Requestの転送量・リクエスト数・レイテンシー、
  費用の実測は未実施**。ローカルParquetの性能がそのままR2に当てはまるわけではない。

## 判断理由・トレードオフ

時刻順Longは今回の条件で最小の容量となり、系列の追加・削除でも
列スキーマを増減させずに済む。Coldの検索頻度が低い運用では、
この利点を優先する。

一方、WideはParquetの列メタデータから系列を発見しやすく、
単一系列検索で必要列だけを取得できる。R2/S3互換ストレージの
HTTP Range Requestを通じてWideの転送量・レイテンシーが有利になる可能性は残る。
Longでは系列一覧の取得方法を別途用意する必要がある場合がある。

容量課金はサービスによって段階制や最低課金単位があり、今回の32.5%の
容量削減が同率の料金削減を意味するわけではない。
ランタイムの転送コスト・オブジェクト取得コストについても実測が必要である。

## 今後の実装前に決める事項

1. メトリクス名・ラベル群・サイト識別子の保存方式、および系列一覧メタデータ。
2. 同一時刻・同一系列の重複サンプルと型の扱い。
3. 1か月分を1ファイルにするか、サイズ上限で分割するか。
4. R2上の実ファイルに対する単純SELECTの性能、読み取り量と料金。
5. Archiverの再実行時の冪等性・ファイル公開手順・検証方法。

これらは初期の時刻順Long採用を妨げないが、本番スキーマと運用仕様の確定は別途行う。
